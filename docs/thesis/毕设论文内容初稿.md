## 摘要

针对研究生阅读多篇论文时文件管理、证据定位、跨文献整理和研究笔记版本追踪分散的问题，本文设计并实现了一套面向单用户本机部署的文献研读工作台。系统由浏览器界面、HTTP API、后台任务 worker、PostgreSQL/pgvector 和本机 PDF 文件卷组成；在需要 OCR、向量生成、重排序或问答时，由后端调用云端模型服务。系统实现了批量 PDF 导入、不可变文献版本、结构化内容单元、向量与全文混合检索、专题范围控制、来源页引用、持久研究任务、成果版本管理以及成对备份与隔离恢复验证。

系统采用 4 篇、共 78 个物理页的示例语料进行阶段性验证。单篇问答演示中，系统对 pass@k 问题返回了可跳转到 PDF 物理第 6 页的引用；首次批量导入的另外 3 篇文献处理了 54 页和 150 个内容单元，新增 3 次 Embedding 请求，已有文献没有新增 Provider 请求。另以隔离数据库验证了一页栅格化扫描页的 OCR、检索和原页预览链路。后端在全新隔离 PostgreSQL 环境中完成 102 项测试；合成规模预检覆盖 100 篇模拟记录，但不等价于真实百篇全链路验收。

目前检索分数仍来自未经人工确认的候选标注，不能作为正式质量结论。真实扫描件质量、100 篇获授权文献及单批 30 篇处理、Q1–Q24 人工复核和正式 Agent 回答评测仍待完成。因此，本文现阶段支持系统工程链路和可靠性实现的说明，尚不支持对学术答案质量或大规模泛化效果作正式结论。

## 第 1 章 绪论

### 1.1 研究背景

研究者在阅读多篇论文时，需要在 PDF 原文、检索工具、问答记录和笔记之间反复切换。若回答没有保留文献版本和物理页来源，后续复核容易失去上下文；若提取文本、OCR 转写与原文不作区分，系统也可能把识别结果误当作可逐字引用的证据。系统设计因此需要同时处理文献导入、证据定位、研究范围隔离和过程可恢复等问题。

本项目将目标限定为一个本机运行的单用户研究工作台。文献原件与业务数据库保存在 Docker 数据卷，模型能力通过后端请求云端服务提供。该部署方式保留本机文件管理和数据库状态，同时要求用户认识到模型请求会将相应文本或图像发送给服务商。与“自动生成答案”相比，本系统更强调来源可回查、研究范围明确和失败后能恢复。

### 1.2 研究目标

本文的工程目标包括：建立支持批量导入和版本保留的文献库；从 PDF 页面抽取正文并形成带物理页信息的检索单元；组合向量召回、关键词召回与重排序；让研究任务在明确专题或文献范围内运行；使问答证据可以跳转到原 PDF；并验证任务中断、取消、索引切换及本机数据恢复等边界。

本文将上述工作作为系统设计与实现，不将模型或检索组件的集成称为新的学术算法。系统质量结论需由人工复核的问题集和正式实验产生，不能从功能实现本身推出。

### 1.3 相关研究与项目定位

检索增强生成将语言模型的参数化知识与外部检索到的非参数化知识结合。Lewis 等提出的 RAG 框架使用稠密向量索引检索上下文，再由序列到序列模型生成答案，并在开放域问答等知识密集任务上进行评估[1]。该工作为“先检索、再生成”的系统流程提供研究背景；其 Wikipedia 语料和实验任务与本项目的本地多论文研读场景不同，因此其指标不能作为本系统效果的依据。

在候选证据召回方面，Karpukhin 等以双编码器学习问题与段落的稠密表示，并在开放域问答基准上与 BM25 等稀疏检索方法比较[2]。稠密表示有助于匹配词面不同但语义接近的表达，而关键词检索仍可响应术语和精确词项。本项目据此将向量召回与全文词项召回作为可分别测量的候选来源，并通过 R1、R2、R3 实验比较；相关论文在其数据和设置下的结果不预设本项目哪种配置更优。

多路召回结果的融合可采用 Reciprocal Rank Fusion（RRF）。Cormack、Clarke 与 Büttcher 将 RRF 作为组合多个检索排序的简单方法，并在 TREC 与 LETOR 等实验中报告其表现[3]。本系统在 R2 中用 RRF 合并向量与关键词排名；该方法的既有实验只支持选择它作为待评估的融合方案，不能替代本语料上的人工标注和对照实验。

在多步研究任务方面，ReAct 研究了交替生成推理步骤和外部动作、通过环境观察继续任务的交互范式，并在问答、事实核查及交互任务上进行了实验[4]。本项目同样让模型通过工具读取资料，但另以白名单、服务端专题范围检查、文献版本固定和引用校验限制工具副作用。这些是本系统的工程安全实现，不是 ReAct 论文提出的结论，也不据此宣称算法创新。

据上述研究，本项目定位为面向单用户本机部署的文献研读系统设计与实现。它把可回查的物理页来源、范围约束和故障恢复作为工程目标；效果是否达到预设阈值仍须由后续冻结语料、人工 qrels 和正式实验验证。该定位是对相关研究与本项目范围的归纳，不代表已经证明系统在学术质量上优于既有方法。

### 1.4 研究范围与约束

当前输入语料为 4 篇示例论文及 8 道原始问题。原始文件与问题文本保持不变并由 SHA-256 清单标识。样本文档共 78 页，均存在可提取的 PDF 文字层；此外，项目建立了合成扫描页和从样本页生成的栅格化测试页，用于验证软件 OCR 链路。合成或栅格化页面不能代表相机拍摄、复印或真实影印件上的 OCR 泛化能力。

产品按单用户本机使用设计，默认服务仅绑定回环地址，目前没有账户认证。系统包含云端模型调用，因此数据是否可以提交须由用户依据资料授权和服务商政策判断。本项目不自行在线收集论文，也不将合成数据作为真实学术语料。

## 第 2 章 需求分析与关键技术

### 2.1 用户需求

系统的主要用户是需要管理多篇论文并围绕研究问题整理证据的单个研究者。围绕该任务，系统需要支持以下操作：批量提交 PDF 并查看逐篇处理状态；保留同一文献的多个文件版本；在阅读页查看原文及解析单元；创建专题并显式关联文献；发起限定范围的研究任务；检查回答引用并回到对应原页；将有用内容保存、编辑和导出。

### 2.2 功能需求

文献导入需要校验文件格式、页数和重复内容；同一文件重复提交不应重复建档或重新调用 OCR/Embedding。解析结果需要保留版本、页码、内容类型及来源状态。检索至少支持向量检索和全文词项检索，并能按文献版本和索引代限制候选范围。

研究任务需要在专题、用户选择的文献或明确的全库范围中执行。工具层必须再次校验访问范围，不能仅依靠模型遵守提示。回答引用需要关联已读取的文献版本和物理页；OCR 等派生内容可以用于定位，但不能自动作为逐字引文。记忆中的研究结论在用户确认前不能作为已确认知识使用。

### 2.3 非功能约束

持久任务采用数据库状态和租约管理，避免 API 或 worker 重启后任务丢失；新索引完整构建前保留旧活动索引；恢复测试不能破坏正式数据卷。模型请求按用途和任务预算控制，不进行隐式自动重试。密钥只进入 API 和 worker，不进入前端、报告或日志。服务默认仅回环监听；单用户设计不等于具备身份认证。

### 2.4 技术组成

前端使用 Vue 3、TypeScript 与 Vite；API 使用 FastAPI；异步工作由独立 Python worker 处理；数据存储使用 PostgreSQL 17 和 pgvector。向量维度配置为 2560，HNSW 使用 halfvec 索引以满足所选向量维度约束。OCR、Embedding、Reranker、视觉理解及对话通过各自用途的 Provider 接口调用。完整组件与数据流见[系统架构与关键流程](../design/系统架构与关键流程.md)。

## 第 3 章 系统设计

### 3.1 总体架构

系统由五类组件构成：浏览器负责交互；FastAPI 提供上传、文献、专题、任务、引用和成果接口；worker 执行 PDF 解析、索引及 Agent 任务；PostgreSQL/pgvector 保存业务状态、任务、内容单元和向量；Docker 文件卷保存 PDF 原件。只有后端 API 和 worker 获得模型 Key。

用户发起导入后，API 先校验并保存文件，按内容哈希识别重复项，再创建持久任务。worker 领取任务并处理 PDF 页面，在需要时调用 OCR，随后生成结构化单元和 Embedding。研究请求创建时记录专题范围、文献版本及索引代；检索、页面读取和记忆工具均在服务端校验相同范围。详细时序和实体关系参见架构说明。

### 3.2 文献和索引数据模型

逻辑文献与文件版本分开建模。每个文献版本保留自己的 PDF 存储键、哈希、状态和页数；页面和内容单元关联到具体版本。内容单元包括正文、公式、表格和图表相关文本，同时记录其来源、是否派生、能否作为逐字引用及可用位置框。Embedding 与索引代关联，使模型或维度变化时可以构建新代而不混用不同向量空间。

### 3.3 专题范围和证据模型

专题可以关联多篇文献；会话中的研究 Run 保存范围快照及其哈希。工具调用读取页面、记忆或其他资源前，服务端检查目标是否属于当前范围。证据记录保存文献版本、页码、内容类型和引用资格。专题记忆与文献证据分开，待确认结论需要用户明确确认；来源版本变化后，旧结论失效。

### 3.4 任务和事件模型

后台任务使用 PostgreSQL 持久化，worker 通过租约领取任务，并以 fencing token 阻止过期 worker 写入新结果。研究 Run、消息、工具调用和事件均持久保存。SSE 支持按游标补发事件；游标过期时返回当前完整状态，最终答案也可由 REST 状态恢复。任务取消可以阻止后续工具及成果副作用，但已发出的同步云端 HTTP 请求无法保证立即中止。

## 第 4 章 系统实现

### 4.1 PDF 导入与解析

上传接口一次最多处理 30 个文件，并为每个文件返回独立结果。系统使用 SHA-256 判断相同文件；新文件创建不可变版本和后台任务。PDF 页面的原生文字层进入正文解析；低文字量页面可进入 OCR 路径。解析器进一步识别公式、表格及带图形区域的图注，并保留物理页信息。派生表格或 OCR 描述的引用资格被单独标记，阅读器可以显示原始 PDF 页面供人工核对。

为了保证重复导入和失败恢复，解析结果及 Embedding 缓存由内容哈希与处理配置键约束。失败版本可重试；新版本处理成功后才激活，不覆盖仍可用的旧版本。文献文件路径由内部生成的存储键解析，并拒绝越界键或符号链接路径。

### 4.2 混合检索

检索流程提供三种可比较配置：R1 为向量召回；R2 为向量与全文词项召回后使用 RRF 融合；R3 在 R2 候选上增加 Reranker。候选结果按唯一物理页聚合，最终返回最多 8 页。检索过程固定文献活动版本、索引代和研究范围，避免答案生成时混入过期版本或其他专题资源。

这些配置是系统实验对象，不意味着 R3 必然优于 R1。正式比较需要人工确认必要证据组，并分别报告开发集和留出集。当前候选标注未满足这一条件。

### 4.3 专题 Agent 与成果版本

专题 Agent 通过受限工具读取文献目录、页面和已确认记忆，并在任务预算内运行。模型输出的工具名称和参数经白名单及 schema 验证；工具执行前还会检查专题范围、文献版本及任务状态。工具调用次数、模型步数、输入输出 token 和运行时间均有限制。

研究者可将完成的 Run 显式保存为成果。成果保留不可变版本，手工修改会递增 revision；模型生成内容作为候选版本，只有用户采纳后才成为当前版本。并发采纳通过 revision 冲突阻止覆盖更新的内容。CSV 导出会转义电子表格公式前缀。

### 4.4 故障恢复、备份与部署

普通入库任务使用租约续期，worker 进程中断后可恢复；Agent 中断后进入等待状态，需由用户明确继续。SSE 连接中断不会自动重复创建 Run，重连按事件游标补取状态。索引重建在新代校验完成后切换，并保留旧代用于已开始查询。

数据库和 PDF 文件卷必须成对备份。项目提供生产文库归档及随机隔离项目恢复验证脚本；恢复时不启动 worker、不注入模型 Key，并核对文件哈希、schema、版本、页数和内容单元。该实现验证了本机隔离恢复，不代表异机、离线灾备或正式卷切换已完成。

## 第 5 章 验证与阶段性结果

### 5.1 验证方法

验证分为单元测试、隔离 PostgreSQL 集成测试、浏览器关键流程及受限真实模型试验。普通测试不配置模型 Key，使用 Provider 夹具；真实请求单独记录用途、次数、token、估算价格与限制。正式质量实验还需要冻结语料、人工 qrels、相同检索参数和完整 R1/R2/R3 排名。

### 5.2 模型可行性探测

M0 对 OCR、视觉、工具调用、Embedding 和 Reranker 做了小样本能力探测，共 7 次计费请求且未自动重试。2560 维 Embedding 返回维数符合配置；一页合成扫描测试页的预设标记均被识别；单张图表裁剪和单次工具调用往返完成。探测只说明接口与基本能力可用，不构成通用 OCR、视觉或检索质量结论，账户账单也未由推理响应精确核验。

### 5.3 单篇与批量链路

M2 在一篇 24 页原生文字 PDF 上贯通导入、Embedding、检索、回答和引用。对 Q3 的 pass@k 问题，浏览器引用可跳转到物理第 6 页，人工核对该页包含对应公式。该次运行共 7 次模型请求，依据可核实公开单价估算成本为 ¥0.025812；这不是账户账单，也不代表问题集上的总体准确率。

M3 首次导入其余 3 篇样本文献，共 54 页和 150 个内容单元；所有单元获得 Embedding，3 篇文献均处理完成，每篇执行 1 次 Embedding 请求。原有 M2 文献没有新增 Provider 请求。批量接口测试覆盖 30 篇上限、逐文件失败结果和重复提交去重。

另在隔离数据库中将样本 PDF 的一页栅格化为无文字层输入，完成 OCR、检索和原页预览。任务调用 OCR 1 次，并对一页结果以整页引用、空摘录的方式返回。该测试验证软件处理链路，不是相机扫描件质量评测。

### 5.4 工程测试与规模预检

后端全量测试在一次性 PostgreSQL/pgvector 数据库中执行，102 项全部通过；测试未配置云端 Key，临时数据库、容器和网络在测试后清理。唯一警告是现有 Starlette/AnyIO 弃用提示。测试结果及环境见[全量回归报告](../../experiments/reports/backend-full-test-run-2026-09-30.json)。

合成基础设施预检使用 100 篇、每篇 20 页、每页 3 个内容单元及 100 个任务。文献列表 p95 为 8.344 ms，任务状态 p95 为 5.211 ms，队列领取与完成 p95 为 11.098 ms，本地混合检索（假 Provider）p95 为 19.166 ms。该数据仅用于基础设施预检，不能视为 100 篇真实论文的 OCR、检索或批量导入验收。

## 第 6 章 讨论与局限

第一，语料规模和代表性有限。当前正式库为 4 篇样本文献；合成 100 篇压力测试不能替代真实语料。A14 所需 100 篇获授权文献及一次 30 篇真实批次尚未完成。

第二，扫描件验证范围有限。原始 78 页都有文字层；OCR 试验使用合成页和从样本文档栅格化的页面，不能推断真实相机扫描或复杂影印版面的准确率。当前引用策略保留原页定位，但派生识别文本不是逐字引文。

第三，评测标注尚未冻结。Q1–Q8 和新增 Q9–Q24 仍待人工复核，拟议 4/2/2 留出集没有冻结。引用支持率、引用覆盖率、回答完成率、缺证处理和安全副作用指标尚无正式人工结果；8 道原题各 3 轮 Agent 实验也未执行。

第四，供应商价格及系统安全范围有限。公开单价估算不等于账户结算；云端在途同步请求无法被客户端强制终止。系统面向单用户本机运行，目前没有登录认证，不应暴露到公网。

第五，交付形态尚未最终确定。学校模板、截止日期、匿名要求和数据归档规范尚未提供；本文件因此是内容初稿，不是格式终稿。相关工作部分目前只选取了与系统设计直接相关的代表性论文，还需依据导师意见扩展，并按学校格式核定引文和参考文献；正式评测结果也需后续补入。

## 第 7 章 结论与后续工作

本文完成了本地文献研读工作台的主要工程实现，包括批量导入、版本化存储、结构化解析、混合检索、专题范围约束、来源引用、任务恢复、成果版本管理和本机备份验证。现有小样本结果表明，关键软件链路能够运行，任务与数据恢复也有隔离环境下的测试证据。

当前证据不足以证明正式学术问答质量或百篇真实文献处理能力。后续应先完成 Q1–Q24 的人工证据标注和留出集冻结，取得获授权的 100 篇文献并执行单批 30 篇验收，补充真实扫描样本，再按冻结配置运行正式检索及 Agent 对照实验。随后依据学校模板更新结果章节、参考文献、摘要和结论，并完成最终交付清单。
