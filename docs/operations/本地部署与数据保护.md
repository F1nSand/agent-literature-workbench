# 本地部署与数据保护

## 启动和停止

要求 Docker Desktop 正常运行。项目根目录执行：

```powershell
docker compose --file compose.production.yaml up --build -d
```

首次启动会构建前端静态资源、拉取运行镜像、运行 Alembic 数据库迁移并启动 API、worker、PostgreSQL、DOCX 转换 sidecar 和 Nginx。访问 `http://127.0.0.1:5174`；健康状态使用 `http://127.0.0.1:5174/api/v1/health/ready`。启动后 readiness 应返回 API 与数据库均就绪。API 和数据库只在 Compose 内部通信；产品 API 仍运行于 distroless 镜像。

产品版 DOCX 转换由独立 LibreOffice sidecar 完成。sidecar 没有宿主机发布端口、模型 Key 或文献共享卷，只接入独立 `internal` Compose 网络；API/worker 通过内部 HTTP 提交有大小限制的文档并接收 PDF。容器以非 root 用户运行，使用只读根文件系统、临时 tmpfs、资源上限、移除 capabilities 和 `no-new-privileges`。转换服务仅用于把 DOCX 生成阅读用 PDF，不保存长期文献副本。开发 Compose 不启动该 sidecar；开发 API 镜像内安装 LibreOffice 并本地转换。生产 API 保持 distroless，不安装 LibreOffice。

支持的文献格式为 PDF、EPUB、DOCX、Markdown 和 TXT。DOCX 原件与转换产物分开保存，阅读器明确提示转换版；字体替换、页眉页脚、分页、表格或嵌入对象可能与 Microsoft Word 呈现不同，页码引用针对转换版。EPUB、Markdown 和 TXT 使用章节/CFI 或稳定段落锚点定位，不将可变的屏幕分页说成原文物理页。

停止服务：

```powershell
docker compose --file compose.production.yaml down
```

产品版与开发版使用同一 Compose 项目名和命名数据卷，不能同时运行。开发调试使用根目录 `compose.yaml` 和 Vite 源码挂载；产品 Compose 使用静态前端镜像，不挂载源码、评测问题或开发计划。

本机当前使用开发后端与编译后的前端预览。Windows Docker 源码挂载下 Vite 开发依赖优化曾使页面请求阻塞，预览覆盖文件用于稳定检查实际界面：

```powershell
docker compose -f compose.yaml -f compose.preview.yaml up -d
```

修改前端源码后需用同样两个文件执行 `up -d --force-recreate --no-deps frontend`，启动时会重新构建前端。此模式没有热更新；它是本机预览，不代表已完成生产发布。仅执行默认 `docker compose up` 会恢复开发服务器模式。默认开发服务器阻塞问题仍需单独排查。

普通 `down` 会保留命名数据卷。`down -v` 会删除 Compose 数据卷，可能永久删除原始文献、派生文件与数据库内容；不要把它当作常规停止命令。

## 密钥和数据边界

在项目根目录 `.env` 配置 `SILICONFLOW_API_KEY`。Compose 只将它传给 API/worker；前端、数据库和迁移容器不接收该值。不要将 `.env` 发给他人、放入截图或提交到代码仓库。云端 OCR、Embedding、Reranker 和 Agent 请求会将相应文本或图像发送给配置的服务商，并可能产生费用。

数据库位于 `postgres_data` 命名卷，原始文献及派生文件位于 `literature_data` 命名卷。二者必须作为同一时间点的一组数据备份：数据库引用文件存储键，单独复制其中一边会造成引用缺文件或文件无索引记录。备份前应停止会写入的 API 和 worker，避免数据库与文件状态不一致。

## 备份与恢复验证

数据库和文献文件卷必须成对备份。执行期间脚本先停止 worker 与 API，导出 PostgreSQL custom dump 和 `literature_data` 文件卷，再恢复原先正在运行的服务并检查 API readiness。默认将备份写到 `%LOCALAPPDATA%\LiteratureWorkbench\Backups`：

```powershell
.\scripts\backup.ps1
```

命令输出会给出新建目录、两个归档的 SHA-256 与数据库文献统计；备份清单 `manifest.json` 保存相同摘要和 schema revision。脚本不会覆盖现有目录，也不会把 `.env` 放进归档。数据库和原始文献本身仍包含研究资料，应保护此目录并另行复制到独立磁盘。

使用某份备份进行隔离恢复检查：

```powershell
.\scripts\restore_test.ps1 -BackupPath 'C:\Users\<用户名>\AppData\Local\LiteratureWorkbench\Backups\<备份目录>'
```

恢复脚本先校验数据库转储及文献卷归档 SHA，再创建随机 Compose 项目与全新数据卷；不启动 worker、不提供模型 Key。它按每个版本固定的文件格式核对原件哈希、schema、活动版本、页和内容单元；DOCX 额外核对 PDF 阅读产物的存在、哈希和物理页数，并核对独立笔记数量。多格式检查的聚焦测试已通过，实际多格式备份归档的隔离恢复演练尚待执行。完成后只清理由本次随机项目创建的临时容器、网络和卷，不切换或覆盖正式文库。合成数据灾备演练只用于内部验收，不属于日常部署步骤。

此前的 PDF 数据备份归档已在隔离卷内验证恢复；多格式数据尚无相同验证。正式卷切换、异机恢复或离线恢复也未自动化。若需要灾难恢复，应先在独立环境核对目标数据和备份，再制定正式切换步骤；不要用 `docker compose down -v` 代替恢复命令。

## 组装与检查发布暂存包

从项目根目录按白名单生成新的暂存目录；不要把项目根目录直接作为发布包，那里可能有 `.env`、用户论文和本机临时文件：

```powershell
python .\scripts\build_release_bundle.py `
  --output .\work\release-candidate `
  --report .\work\release-candidate-audit.json `
  --manual-review-manifest .\work\media-review.json
```

组包器只复制应用源码、锁定依赖、运行脚本及部署/架构说明；不复制 `.env`、论文和问题集、评测材料、实验报告、开发计划、浏览器截图或构建缓存。文本/文件检查 `failed` 时不会创建目标包；没有匹配的人工复核记录时，图像会使暂存包保持 `needs_manual_review`。

`--manual-review-manifest` 是可选参数，只能用于实际检查过的媒体文件。它接受 `reviewer`、UTC 时间 `reviewed_at_utc`、`review_method`，以及文件包内相对路径和 SHA-256 清单，例如：

```json
{
  "schema_version": 1,
  "reviewer": "Reviewer name",
  "reviewed_at_utc": "2026-09-30T13:42:55Z",
  "review_method": "Browser visual inspection",
  "files": [
    {
      "path": "frontend/public/research-desk.svg",
      "sha256": "lowercase-64-character-sha256"
    }
  ]
}
```

示例中的复核者、时间、文件路径和摘要均为格式占位符。实际使用时必须填写真实复核者、UTC 复核时间、包内实际相对路径，以及检查后文件的真实 SHA-256；不能将示例值当作复核证据。

组包时该清单会作为 `RELEASE-MANUAL-REVIEW.json` 放入候选包，并由 `RELEASE-MANIFEST.json` 一并哈希。路径或 SHA-256 与包内当前文件不完全匹配、字段无效或目标不是媒体文件时，审计失败；素材之后发生任何变化都要重新检查并生成新哈希。SVG 仍会接受常见密钥与个人路径文本扫描，人工记录不会绕过这些检查。未提供记录或其他不透明文件未处理时，状态仍是 `needs_manual_review`。可对暂存包再次运行审计：

```powershell
python .\work\release-candidate\scripts\release_audit.py `
  .\work\release-candidate `
  --report .\work\release-candidate-final-audit.json
```

审计会拒绝环境密钥/私钥文件、PDF 原文、数据库/备份归档、符号链接及 `.git`、`work`、`.playwright-mcp`、缓存和依赖目录，并扫描文本中的常见密钥和个人绝对路径。其他格式的原始文献也不得进入发布暂存包；图片可以用精确哈希复核清单记录，Office 文件和其他不透明二进制仍需单独处理。`RELEASE-MANIFEST.json` 包含包内相对路径、大小和 SHA-256，也覆盖人工复核清单本身。此步骤不判断论文授权、不代替 A01–A16 验收，也不代表发布批准；报告路径必须在暂存包之外并且尚不存在。

发布镜像构建后，再显式指定镜像标签扫描历史层（包括最终文件系统中已删除的文件）；报告仍放在候选包目录之外：

```powershell
docker compose --project-name lw-release-candidate --file .\work\release-candidate\compose.production.yaml config --quiet
docker compose --project-name lw-release-candidate --file .\work\release-candidate\compose.production.yaml build api worker frontend migrate converter

python .\work\release-candidate\scripts\audit_docker_image_layers.py `
  lw-release-candidate-api:latest lw-release-candidate-worker:latest lw-release-candidate-frontend:latest lw-release-candidate-migrate:latest lw-release-candidate-converter:latest `
  --report .\work\docker-image-layer-audit.json
```

镜像检查不启动容器、不访问数据卷，也不调用模型服务；它扫描镜像配置、OCI 构建证明元数据及所有引用层中的常见密钥、个人绝对路径、环境/私钥文件和 PDF/备份归档。该检查不涵盖 CVE、许可证、恶意行为或镜像来源证明。镜像标签应替换为实际构建结果；报告必须是新路径。

## 故障时的检查顺序

1. 检查 Docker Desktop 是否运行，再查看 `docker compose ps` 服务状态。
2. 查询 `/api/v1/health/live` 与 `/api/v1/health/ready`，区分 API 进程和数据库依赖。
3. 若 API 已启动但任务不前进，检查 worker 容器状态；先读取错误码和任务状态，再决定是否重试。
4. 不要因 API 重启而清空数据库或文献文件卷。文献原件及完成任务均有持久化状态。
5. 云端请求已发出时，界面取消只能阻止后续操作；当前同步请求无法强制停止服务商侧计算。

## 安全边界

应用按单用户本机使用设计，没有账户认证。默认服务端口仅绑定 `127.0.0.1`。跨站写请求来源检查不是身份认证；保持回环绑定，不要通过路由器或反向代理公开服务。
